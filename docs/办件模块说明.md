# 办件管理模块说明（前端 + 后端 + 权限）

本文档对应「办件管理」功能：在原有 `/api/cases` 六个接口之上，补齐了前端页面、权限体系、分页与关联字段，并给出数据库变更与验证方式。

- 后端代码：`admin-backend/src/**`
- 前端代码：`admin-frontend/src/**`
- 数据库变更：`admin-backend/db/2026-11-case-module.sql`
- SQL 执行器：`admin-backend/db/run-sql.js`

---

## 1. 整体链路

```text
登录 login
  └─ 后端按 roles 推导 permissions 一起返回
       └─ 前端存 user store（roles 控菜单 / permissions 控按钮）
            ├─ 路由 meta.roles      → 决定「办件管理」菜单是否出现、能否直接访问
            ├─ 后端 requirePerms    → 决定接口能否调用（最终防线）
            └─ hasPerms()           → 决定新增/编辑/删除/推进按钮是否展示
```

页面 → 接口对应：

```text
views/cases/index.vue
  ├─ api/cases.ts  → POST /api/cases            （列表 + 分页 + 筛选）
  ├─ CaseFormDialog      → POST /api/cases/add、/api/cases/update
  ├─ CaseDetailDrawer    → GET  /api/cases/:caseguid（主表 + 阶段时间轴）
  ├─ CaseStageDialog     → POST /api/cases/:caseguid/stage
  └─ 删除                → POST /api/cases/delete
```

## 2. 权限设计

### 2.1 权限码

| 权限码 | 含义 | 作用接口 |
| --- | --- | --- |
| `case:view` | 查看办件列表与详情 | `POST /api/cases`、`GET /api/cases/:caseguid` |
| `case:create` | 新增办件 | `POST /api/cases/add` |
| `case:update` | 编辑办件基础信息 | `POST /api/cases/update` |
| `case:delete` | 删除办件及其阶段 | `POST /api/cases/delete` |
| `case:process` | 推进阶段（处理办件） | `POST /api/cases/:caseguid/stage` |
| `*:*:*` | 通配权限，等价于拥有全部 | 全部接口 |

### 2.2 角色 → 权限矩阵

| 角色码 | 角色名称 | view | create | update | delete | process |
| --- | --- | :---: | :---: | :---: | :---: | :---: |
| `admin` | 系统管理员 | ✅ | ✅ | ✅ | ✅ | ✅ |
| `manager` | 办件主管 | ✅ | ✅ | ✅ | ✅ | ✅ |
| `operator` | 办件受理员 | ✅ | ✅ | ❌ | ❌ | ❌ |
| `handler` | 办件办理人 | ✅ | ❌ | ❌ | ❌ | ✅ |
| `viewer` | 办件查看员 | ✅ | ❌ | ❌ | ❌ | ❌ |
| `common` | 普通用户（历史默认） | ❌ | ❌ | ❌ | ❌ | ❌ |

> `common` 是脚手架历史默认角色，不授予任何办件权限，因此这类账号看不到「办件管理」菜单。

### 2.3 权限怎么算出来的

唯一可信来源是后端 `admin-backend/src/constants/permission.js`：

```js
resolvePermissions(roles, extraPermissions)
  ├─ roles 含 admin            → 返回 ['*:*:*']
  ├─ 其余角色取 ROLE_PERMISSIONS 并集
  └─ 再叠加 sys_user.permissions 中显式配置的权限码
```

好处：

- 改角色即生效：登录 `/api/auth/profile`、刷新 token、每次校验 token 时都会重新按库中角色推导（`auth.service.js` 的 `buildProfile`）。
- 不需要逐个维护权限码：`sys_user.permissions` 只在「临时给某人追加单项权限」时才需要填。
- 用户管理页保存角色时会把 `permissions` 清空，避免旧权限残留导致越权。

### 2.4 三层拦截

| 层 | 位置 | 行为 |
| --- | --- | --- |
| 菜单 / 页面 | 路由 `meta.roles`（`src/router/modules/cases.ts`） | 角色不匹配时菜单不显示；直接输 URL 会被路由守卫跳到 403 |
| 接口 | `requirePerms(...codes)`（`middlewares/auth.middleware.js`） | 无权限返回 `code: 403`，HTTP 仍为 200（沿用项目约定） |
| 按钮 | `hasPerms(CASE_PERMISSIONS.X)`（`utils/auth.ts`） | 无权限的按钮不渲染，避免点了才报错 |

### 2.5 如何给用户授权

1. 用 `admin` 账号登录（库中已有的管理员账号，`roles='admin'`）；
2. 进入「用户管理」→ 编辑用户 → 角色下拉勾选（可多选）→ 保存；
3. 该用户重新登录（或等 token 自动刷新）后生效。

SQL 直接授权（等价于页面操作）：

```sql
-- 授予办件主管
UPDATE `sys_user` SET roles = 'manager', permissions = '' WHERE username = 'suncheng';
-- 追加单项权限（角色之外的临时授权）
UPDATE `sys_user` SET permissions = 'case:delete' WHERE username = 'suncheng';
```

### 2.6 首个管理员从哪来

迁移脚本最后一条语句做了引导：**系统里还没有 admin 时，把 id 最小的启用用户设为 admin**。当前库里已存在 `admin` 账号（`roles='admin'`、`permissions='*:*:*'`），所以这条语句实际影响 0 行，不会覆盖任何人的角色。

## 3. 数据库变更

本次没有新增表，复用已有的 `sys_user.roles / sys_user.permissions` 与 `biz_case / biz_case_stage`，只补了索引、排序规则与一个缺口字段来源：

| 变更 | 原因 |
| --- | --- |
| `biz_case` 增加 `idx_biz_case_apply_time(apply_time)` | 列表无筛选时按申请时间倒序取第一页；已有的 `(userid, apply_time)`、`(status, apply_time)` 都以 userid/status 开头，撑不起纯时间排序 |
| `biz_case.userid` 排序规则改为 `utf8mb4_0900_ai_ci` | 与 `sys_user.userid` 保持一致，否则两表 `LEFT JOIN` 会报 `Illegal mix of collations` |
| `sys_user.roles / permissions` | 已存在，本次开始真正被使用（角色码 + 推导权限） |

建表语句里原本就有 `uk_caseguid`、`uk_case_no`、`idx_userid_apply`、`idx_status_apply`、`idx_business_name`、`idx_caseguid_sort`，这些**不需要再建**：唯一约束已由 `uk_case_no` 承担，`userid` / `status` 的单列索引是复合索引的最左前缀，重复创建只会增加写入成本。

「申请人姓名」不需要新字段：列表与详情都用 `LEFT JOIN sys_user` 取 `real_name AS applicant_name`。

执行方式：

```bash
cd admin-backend
node db/run-sql.js db/2026-11-case-module.sql
```

脚本可重复执行，重复建索引会打印「已存在」并跳过。

## 4. 接口清单

统一约定：HTTP 恒为 200，业务结果看 `code`（200 成功 / 400 参数错误 / 403 无权限 / 404 不存在 / 500 服务器错误）；除登录相关接口外都需要 `Authorization: Bearer <accessToken>`。

### 4.1 新增办件

```http
POST /api/cases/add        权限：case:create
```

请求体：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `userid` | 否 | 申请人 userid（UUID）。**不传时取当前登录人** |
| `businessName` | 是 | 业务名称 |
| `deptName` / `consultPhone` / `handlerName` / `applyTime` / `remark` | 否 | 空字符串会被清洗成 null |
| `status` | 否 | 默认 1（待受理） |

行为：服务端生成 `caseguid`（UUID v4）与 `case_no`（`BJ + YYYYMMDD + 4 位流水`），同一事务内插入首个「受理」阶段（状态 2 进行中）；`handlerName` 未传时默认当前登录人昵称。

返回：`{ caseguid, case_no }`

### 4.2 办件列表（分页）

```http
POST /api/cases            权限：case:view
```

请求体（全部可选，条件之间 AND）：

| 字段 | 说明 |
| --- | --- |
| `userid` | 精确匹配申请人 |
| `caseNo` | 办件编号，模糊匹配 |
| `businessName` | 业务名称，模糊匹配 |
| `status` | 状态精确匹配，允许 0 |
| `scope` | 传 `mine` 时只查「申请人 = 当前登录人」，优先于 `userid` |
| `page` / `pageSize` | 默认 1 / 10，`pageSize` 上限 100 |

返回：

```json
{
  "code": 200,
  "message": "查询成功",
  "data": { "list": [], "total": 0, "page": 1, "pageSize": 10 }
}
```

> 与改造前相比，`data` 由数组变成 `{ list, total, page, pageSize }`，排序为 `apply_time DESC, id DESC`。

### 4.3 办件详情

```http
GET /api/cases/:caseguid   权限：case:view
```

返回主表字段 + `applicant_name` + `stages[]`（按 `sort_no` 升序），一次请求拿全，前端不再二次查询。

### 4.4 更新办件

```http
POST /api/cases/update     权限：case:update
```

`caseguid` 与 `businessName` 必填；**全量更新语义**：未传的可选字段会被清空，`status` 不传会回到 1，所以前端编辑时提交完整字段（含 `status`、`finishTime`）。

办件已结束或已开始流转时返回 `code: 409`（见 5.1 动作规则），不会写入任何字段。

### 4.5 删除办件

```http
POST /api/cases/delete     权限：case:delete
```

事务内先删阶段再删主表，主表删不到则回滚并返回 404。办件已结束或已开始流转时返回 `code: 409`。

### 4.6 推进阶段

```http
POST /api/cases/:caseguid/stage   权限：case:process
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `stageName` | 是 | 新阶段名称，如 受理 / 审核 / 办结 |
| `caseStatus` | 是 | 推进后的办件状态，3 = 已办结 |
| `handlerName` / `deptName` / `opinion` | 否 | 未传办理人时记为当前登录人 |

一个事务内完成三件事：锁主表行（`FOR UPDATE`）→ 结束所有「进行中」阶段并写 `end_time` → 插入新阶段（`sort_no = max + 1`），同时同步主表 `status / handler_name / dept_name`，办结时写 `finish_time`。

办件处于终态（已办结 / 已驳回 / 已撤销）时返回 `code: 409`，不允许继续推进。

### 4.7 人员选项（新增）

```http
GET /api/users/options     权限：case:view 或 case:create
```

只返回启用状态人员的 `{ userid, realName, username }`，供办件表单选择申请人与办理人，不暴露手机号、邮箱。该路由必须放在 `/api/users/:userid` 之前。

## 5. 状态机

办件状态（`biz_case.status`）：

```text
1 待受理 ─┬─► 2 办理中 ──► 3 已办结
          ├─► 4 已驳回
          └─► 5 已撤销
```

阶段状态（`biz_case_stage.status`）：`1 未开始 / 2 进行中 / 3 已完成 / 4 已驳回`。

规则要点：

- 新建办件一定有一个「进行中」阶段，时间轴不会为空；
- 推进阶段只会关闭「进行中」的旧阶段，历史节点只增不改；
- 推进到「已办结」时，新阶段自身也立即标记完成并带 `end_time`，末尾不会挂一个永远进行中的节点；
- 前端「推进后状态」默认 `2 办理中`，办结需要显式选择 `3 已办结`。

### 5.1 办件动作规则（业务约束）

判断依据有两条：主表状态 `status`，以及「已流转到的最大阶段序号」`max_stage_no`（> 1 说明已经开始流转）。

| 办件状态 | 编辑 | 删除 | 推进 | 查看详情 |
| --- | :---: | :---: | :---: | :---: |
| 1 待受理（仅有初始阶段，`max_stage_no = 1`） | ✅ | ✅ | ✅ | ✅ |
| 1 待受理（但已流转） | ❌ | ❌ | ✅ | ✅ |
| 2 办理中 | ❌ | ❌ | ✅ | ✅ |
| 3 已办结 / 4 已驳回 / 5 已撤销（终态） | ❌ | ❌ | ❌ | ✅ |

一句话概括：

- **终态只能看**：已办结、已驳回、已撤销视作办件结束，编辑/删除/推进全部拒绝；
- **开过单就只能推进**：已经开始流转的办件不允许再编辑业务字段或删除，避免中途篡改与痕迹丢失；
- 只有「待受理且未流转」的办件可以编辑与删除。

实现方式：

- 后端：`case.service.js` 的 `getCaseActionRule()` 是唯一判定入口，`update` / `delete` / `stage` 三个接口在写库前调用它，不满足条件返回 `code: 409` 与原因文案（`办件已结束，只能查看详情` / `办件已开始流转，不能编辑或删除` / `办件已结束，不能再推进阶段`）。前端按钮置灰只是提示，绕过 UI 直接调接口同样会被拒。
- 数据来源：列表与详情 SQL 通过子查询 `MAX(sort_no)` 返回 `max_stage_no`，不需要额外请求。
- 前端：`constants/case.ts` 的 `getCaseActionState(status, maxStageNo)` 与后端规则一一对应，列表与详情抽屉共用同一份判断。

## 9. 已知限制

1. **数据权限只到角色级**：拥有 `case:view` 就能看到全部办件；「只看我的」是前端筛选（`scope=mine`），不是强制隔离。若要「受理员只能看自己创建的」，需要在 `findCasesPage` 里按 `request.user` 追加条件。
2. **办件编号仍非并发安全**：唯一索引能挡住重复，但两个并发请求会有一个失败返回 500，而不是自动重试。要彻底解决需要序号表或 `GET_LOCK`。
3. **附件未与办件关联**：`attachment` 表与 `/api/files` 已存在，但 `biz_case` 没有 `case_guid` 关联字段，办件暂时不能挂材料。
4. **角色只支持「并集」授权**：没有「本人数据」和「本部门数据」这类细粒度规则。
